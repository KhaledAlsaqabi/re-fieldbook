01

Initial Assessment Methodology

What to do in the first five minutes, before a disassembler is even open.

Static assessment workflow

Work top-down. Each step should take seconds and can rule out entire classes of technique — don't open Ghidra until you know what you're opening it on.

  1. Identify the container. file ./target — architecture, bitness, endianness, static/dynamic linking, stripped status.
  2. Hash it for correlation against VirusTotal / known-sample databases and to detect if a "patched" copy changed. sha256sum ./target.
  3. Check for packing before doing anything else — a packed binary's strings and imports are meaningless until unpacked.
  4. Pull strings in both narrow and wide encodings; grep for flag formats, URLs, format strings, and library version banners.
  5. Enumerate imports/exports — the import table is a free summary of what the binary does.
  6. Run it in an isolated VM/container with strace/ltrace or Procmon — dynamic behavior is often faster than static reading.
  7. Open in a decompiler only once the above narrows the search space.
  8. Set up dynamic analysis (debugger, Frida, or emulator) matched to what step 6 revealed.
Quick wins first

Before any real reversing: strings target | grep -iE 'flag|CTF\{|pico|key|secret', then ltrace ./target. A meaningful fraction of easy CTF binaries fall to these two commands alone.

Packing compresses/encrypts the real code and wraps it in a small stub that decompresses it at runtime. Protectors (VMProtect, Themida) go further and virtualize code into custom bytecode.

Common Scenarios, Anti-Analysis & Reversing Patterns

Recognizing what the compiler emitted, and defeating what the author added on top.

Control flow: source → x86-64 / ARM

x86-64 · if/else
cmp   edi, 10
jle   .else_branch     # inverted condition
    ... ; if-body
    jmp .end
.else_branch:
    ... ; else-body
.end:
ARM64 · if/else
cmp   w0, #10
b.le  .else_branch
    ... // if-body
    b   .end
.else_branch:
    ... // else-body
.end:

Rule of thumb: the compiler almost always inverts the source condition and jumps past the "true" branch.

Automation, Symbolic Execution & Auto-Flag Scripts

Let the machine do the case analysis. Four tools cover 90% of automatable CTF reversing.

Z3 for mathematical / constraint checks

python · z3 flag recovery
from z3 import *

FLAG_LEN = 20
s = Solver()
flag = [BitVec(f'c{i}', 8) for i in range(FLAG_LEN)]
for c in flag:
    s.add(c >= 0x20, c <= 0x7e)
s.add(flag[0] == ord('f'), flag[1] == ord('l'), flag[2] == ord('a'), flag[3] == ord('g'))

acc = BitVecVal(0, 32)
for i, c in enumerate(flag):
    acc = (acc ^ ZeroExt(24, c)) * 0x1000193
s.add(acc == 0xDEADBEEF)

if s.check() == sat:
    m = s.model()
    print(bytes([m[c].as_long() for c in flag]))

python · repeating-key XOR key-length recovery
from itertools import combinations

def hamming(a, b):
    return sum(bin(x ^ y).count('1') for x, y in zip(a, b))

ct = open('cipher.bin', 'rb').read()
scores = []
for klen in range(2, 41):
    chunks = [ct[i:i+klen] for i in range(0, klen*4, klen)]
    dist = sum(hamming(a, b) for a, b in combinations(chunks, 2)) / klen
    scores.append((dist, klen))
best_klen = sorted(scores)[0][1]

# then: split ct into `best_klen` interleaved columns, single-byte XOR-crack each

Symmetric Crypto

Block and stream ciphers fail almost exclusively through misuse, not broken math.

Block cipher modes at a glance

ModeNeedsCommon failure
ECBNothing extraIdentical plaintext blocks → identical ciphertext blocks (pattern leakage)
CBCRandom IVBit-flipping (attacker-controlled plaintext via prior block edits), padding oracle, IV reuse
CTRUnique nonce per messageNonce reuse → XOR the two ciphertexts to get XOR of plaintexts (crib-drag from there)
OFBUnique IVSame as CTR — keystream reuse on IV reuse
GCMUnique nonce, integrity tagNonce reuse leaks the authentication key (forgery), not just plaintext

ECB detection & CBC bit-flipping

python · ECB detection
def looks_like_ecb(ct: bytes, block=16) -> bool:
    blocks = [ct[i:i+block] for i in range(0, len(ct), block)]
    return len(blocks) != len(set(blocks))   # any repeated block = ECB tell
python · CBC bit-flipping
# Flipping a byte in ciphertext block N flips the SAME byte position
# in the decrypted plaintext of block N+1 (and garbles block N itself).
def flip_byte(ct: bytearray, block_idx: int, byte_idx: int, xor_delta: int, block=16):
    pos = block_idx * block + byte_idx
    ct[pos] ^= xor_delta
    return ct
# xor_delta = ord(current_plaintext_char) ^ ord(target_char)

Padding oracle attack (PKCS#7 / CBC)

If the server distinguishes "bad padding" from "bad MAC/data" in its error response or timing, the entire plaintext can be recovered without the key — one byte at a time, per block, using only decryption-side feedback.

  1. Take the target ciphertext block C1 and the preceding block (or IV) C0.
  2. Replace C0 with an attacker-controlled block, brute-forcing its last byte until the oracle reports valid padding (\x01).
  3. That reveals I1[15] = guess ^ 0x01 where I1 is the block cipher's raw decryption output.
  4. XOR with the real C0[15] to recover P1[15], the actual plaintext byte.
  5. Repeat for \x02\x02, \x03\x03\x03 … working backward through the block, then slide to the next block.
Don't hand-roll it

Use PadBuster or Python's paddingoracle library against a real oracle — the byte-by-byte loop above is easy to get subtly wrong (especially the "intermediate byte re-fix" step after the first byte is found per block).

Stream cipher & keystream reuse

python · two-time pad (XOR key/nonce reuse)
# c1 = p1 ^ k, c2 = p2 ^ k  =>  c1 ^ c2 = p1 ^ p2 (key cancels out)
xored = bytes(a ^ b for a, b in zip(c1, c2))
# crib-drag: XOR `xored` with guessed common words (" the ", " and ")
# wherever the result is mostly printable, you've likely found overlapping plaintext
03

RSA

The single most attacked primitive in CTF crypto — almost every break comes from a parameter choice, not the math itself.

Parameters & sanity checks

  • Is e small (3, 5, 17, 65537)? → check for low-exponent attacks first
  • Is N small enough to factor directly? factordb.com before writing any code
  • Are multiple public keys given? → check for shared factors via pairwise GCD, or a common modulus
  • Is p or q close to sqrt(N)? → Fermat factorization
  • Is d unusually small relative to N? → Wiener's attack

Factoring a weak N

p, q close togetherFermat factorizationRsaCtfTool --attack fermat, or manual sqrt-loop

Everything else / unknownThrow the whole kitchen sink at itRsaCtfTool -n N -e e --uncipher C --attack all
python · Fermat factorization
import gmpy2

def fermat_factor(n):
    a = gmpy2.isqrt(n) + 1
    b2 = a*a - n
    while not gmpy2.is_square(b2):
        a += 1
        b2 = a*a - n
    b = gmpy2.isqrt(b2)
    return int(a - b), int(a + b)   # p, q
python · Wiener's attack for small private exponent d
from Crypto.Util.number import long_to_bytes
from owiener import attack   # pip install owiener

d = attack(e, n)     # returns private exponent if it's below ~ N**0.25
if d:
    m = pow(c, d, n)
    print(long_to_bytes(m))

Multi-ciphertext / multi-key attacks

python · batch-GCD across many public moduli
import math
# given a list of (N_i) from many "independent" RSA keys sharing a bad prime source
for i in range(len(ns)):
    for j in range(i+1, len(ns)):
        g = math.gcd(ns[i], ns[j])
        if g != 1:
            p = g; q_i = ns[i]//g; q_j = ns[j]//g
            print(f"shared factor between key {i} and {j}: {g}")
RSA-CRT fault attack

If a signer using CRT-optimized RSA ever produces one faulty signature (bit-flip during computation, glitching), gcd(s_faulty^e - m, N) recovers a prime factor outright — one bad signature is enough to fully break the key.

04

ECC & Signatures

Elliptic-curve failures are almost always nonce or curve-validation mistakes, not the discrete log problem itself.

ECDSA nonce reuse

ECDSA signs with a per-signature secret nonce k. Reuse k across two signatures (or use a biased/predictable PRNG for it) and the private key falls out algebraically.

python · recover private key from repeated nonce
# Two signatures (r, s1) and (r, s2) — same r means same k was used
def recover_privkey(r, s1, s2, z1, z2, n):
    k = ((z1 - z2) * pow(s1 - s2, -1, n)) % n
    priv = ((s1 * k - z1) * pow(r, -1, n)) % n
    return priv, k

Even without exact reuse, a nonce that leaks a few bits per signature across many signatures (biased LCG, truncated nonce) is solvable via the Hidden Number Problem using lattice reduction — see SageMath's LLL-based HNP solvers.

Hashing & PRNGs

Where "just a hash" or "just random" is doing more work in the exploit than it looks.

Hash length extension attack

Merkle–Damgård hashes (MD5, SHA-1, SHA-256) leak internal state in their output — if a server computes MAC = H(secret || message) without a construction like HMAC, an attacker who knows H(secret||message) and len(secret) can forge H(secret || message || padding || extra) without ever knowing secret.

hashpump -s '6bc1e6...' -d 'original_message' -a ';admin=true' -k 16
# outputs the new hash AND the exact byte string to send (with correct padding baked in)

Toolbox & Workflow

The short list that resolves most crypto challenges without writing custom math.

Core tools

Throws ~20 known RSA attacks at a given N/e/c automatically — always the first thing to try on an RSA challenge.

Lattice reduction (LLL), elliptic curve arithmetic, polynomial roots (Coppersmith) — anything requiring real number theory.

Automated CBC padding-oracle exploitation against a live decryption oracle.

Triage flowchart

  1. Is it printable and structured (Base64/hex/etc.)? Decode fully before assuming encryption.
  2. Is a key/modulus given? Identify the primitive (RSA parameters, AES mode, curve name) precisely.
  3. For RSA: run RsaCtfTool with --attack all before anything manual.
  4. For block ciphers: check for ECB pattern leakage, then check if you control any plaintext (bit-flipping / padding oracle).
  5. For signatures: check for repeated/biased nonces across multiple signatures.
  6. For "random" values: count how many outputs you can observe — 624 outputs breaks Python's random completely.
  7. Nothing above fits? Re-read the challenge name and source for a hint at a named, unusual construction — CTF crypto challenges are rarely generic textbook RSA/AES without a twist.
